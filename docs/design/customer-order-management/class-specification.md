# Customer, Address, Package and Order Management — Class Specification

## 1. Scope and mapping conventions

This document specifies the proposed ASP.NET Core 8 API design for SRS FR-06–FR-12 and related customer use cases UC-03–UC-08 and UC-10. It describes contracts and responsibilities only; it does not implement C# types, controllers, or endpoints.

The entity columns and relationships below align with the existing PostgreSQL ERD and EF Core model. Request DTO validation and endpoint contracts are proposed API-boundary behavior.

| C# / domain type | PostgreSQL representation | Notes |
|---|---|---|
| `Guid` | `uuid` | Primary/foreign keys use UUIDs. |
| `decimal(p,s)` | `numeric(p,s)` | Preserve the precision/scale defined by the ERD (for example, coordinates `numeric(9,6)`). |
| `DateTime` / `DateTime?` | `timestamp with time zone` (`timestamptz`) | Persist UTC instants; nullable CLR values map to nullable columns. The ERD's DBML uses generic `timestamp`, while the EF Core migrations specify `timestamp with time zone`. |
| `OrderStatus` | `varchar(30)` | The eight values below are the domain enum; the current entity stores `Status` as `string`, with a varchar column. If the CLR property becomes an enum, configure and test EF Core string conversion and enum validation. |
| `bool` | `boolean` | Required unless the ERD marks the property nullable. |
| `string` / `string?` | `varchar(n)` / `text` | Required strings are non-null; optional strings are nullable. `varchar` lengths follow ERD/EF configuration. |
| `long` identity | `bigint` identity | Used for `DeliveryStatusLog.Id`. |

`PK` means primary key; `FK` means foreign key. Property names are C# PascalCase; storage names are the corresponding snake_case ERD column names.

## 2. Entity specification

All entity properties are mapped to columns unless noted as a navigation. Defaults below reflect the existing model where specified; business validation is additional to database nullability.

|---|---|---|---|
| `Id` | `Guid` / `uuid` | PK, NOT NULL | Generated UUID. |

| `CreatedAt`, `UpdatedAt` | `DateTime` / `timestamptz` | NOT NULL | UTC timestamps; creation/update times. |
| Navigations | — | — | Required customer, package, origin and destination; optional dispatcher, address, mission and ETA; zero or more status logs and notifications. |

#### OrderStatus values

The enum has exactly eight stored values:

| Value | Meaning |
|---|---|
| `PENDING` | Order submitted and awaiting dispatcher review. |
| `APPROVED` | Dispatcher approved the request. |
| `READY_FOR_TAKEOFF` | Package intake at origin is confirmed and the order is prepared for flight. |
| `IN_TRANSIT` | Delivery is in progress. |
| `ARRIVED` | Package/drone arrived at the destination awaiting pickup confirmation. |
| `DELIVERED` | Recipient completed pickup with the secure code. |
| `CANCELLED` | Order was cancelled under an allowed rule. |
| `FAILED` | Delivery attempt failed. |

Only valid state transitions may be applied; every transition must be logged. The precise transition matrix is owned by the delivery workflow and must remain consistent with the SRS/business process model.

## 3. DTO specification and validation

Validation attributes run at the API boundary. Services must still enforce ownership, cross-field rules, state eligibility, and database uniqueness. `[Phone]` is the .NET `PhoneAttribute`; it is a format check, not proof that the number is reachable.

For non-nullable `Guid` request properties, reject `Guid.Empty` explicitly; `[Required]` alone does not reject it. Apply the same non-empty check to an optional ID whenever it is supplied.

| DTO | Properties and validation |
|---|---|
| `CreateCustomerAddressDto` | `Label`: `[Required]`, `[MaxLength(50)]`; `ContactName`: `[Required]`, `[MaxLength(150)]`; `ContactPhone`: `[Required]`, `[Phone]`, `[MaxLength(20)]`; `AddressLine`: `[Required]`; `Latitude`, `Longitude`: nullable `[Range]` (-90..90 and -180..180 respectively); `IsDefault`: `bool`. Add cross-field validation requiring coordinates together. |
| `UpdateCustomerAddressDto` | Same editable fields and rules as create; the customer ID is derived from claims and is not accepted in the body. |
| `CustomerAddressResponseDto` | `Id`, `Label`, contact name/phone, address line, optional coordinates, `IsDefault`, timestamps. No owner credentials or navigation objects. |
| `CreatePackageDto` | `PackageName`: `[Required]`, `[MaxLength(200)]`; `WeightGram`: `[Range(typeof(decimal), "0.01", "5000")]`; `LengthCm`: `[Range(typeof(decimal), "0.01", "40")]`; `WidthCm`, `HeightCm`: `[Range(typeof(decimal), "0.01", "30")]`; `PackageImageUrl`: optional validated URL/reference; `IsFragile`: `bool`. |
| `UpdatePackageDto` | Same editable fields and numeric constraints as create; sender ID comes from claims. Service rejects updates that violate an existing order's invariants. |
| `PackageResponseDto` | `Id`, name, weight, dimensions, optional image reference, fragile flag, creation time. |
| `CreateDeliveryOrderDto` | `PackageId`, `OriginStationId`, `DestinationStationId`: `[Required]`; `DeliveryAddressId`: optional; `RecipientName`: `[Required]`, `[MaxLength(150)]`; `RecipientPhone`: `[Required]`, `[Phone]`, `[MaxLength(20)]`. No `CustomerId`, status, tracking number, or secure code supplied by client. |
| `UpdateDeliveryOrderDto` | The DTO contains exactly four fields: `RecipientName`: `[Required]`, `[MaxLength(150)]`; `RecipientPhone`: `[Required]`, `[Phone]`, `[MaxLength(20)]`; `DestinationStationId`: non-empty `Guid` referencing a valid destination station; `DeliveryAddressId`: optional nullable `Guid` referencing an address owned by the customer. No `PackageId`, `OriginStationId`, or `Status` field is permitted. Accepted only while status is `PENDING`. |
| `CancelDeliveryOrderDto` | `CancellationReason`: `[Required]`, `[MaxLength(500)]`; maps to `DeliveryOrder.CancelReason` / database `cancel_reason`. Service verifies the current order state permits cancellation. |
| `ConfirmDeliveryDto` | `SecureCode`: `[Required]`, exactly six decimal digits; compare securely and apply the agreed attempt/lockout policy. |
| `DeliveryOrderFilterParams` | Optional `Status` (must be one of `OrderStatus`), `TrackingNumber`, `OriginStationId`, `DestinationStationId`, `FromCreatedAt`, `ToCreatedAt`; `Page`: `[Range(1, int.MaxValue)]`; `PageSize`: `[Range(1, 100)]`. Require `FromCreatedAt <= ToCreatedAt`. |
| `DeliveryOrderDetailResponseDto` | `Id`, tracking number, status, package summary, origin/destination summaries, optional delivery address summary, recipient name/phone, timestamps, status-history list. Never serialize `PickupSecureCode` in the general detail DTO. |
| `DeliveryStatusLogResponseDto` | `FromStatus`, `ToStatus`, optional remarks/actor display, UTC `CreatedAt`. |
| `NotificationResponseDto` | `Id`, optional `OrderId`, type, title, message, read flag, created/read timestamps. |

## 5. Proposed API/controller contract

All listed routes require authentication and role `CUSTOMER`. IDs are scoped to the caller; a foreign owner's resource must not be disclosed. `201` applies to successful creates, `200` to successful reads/updates/actions returning content, and `204` to successful no-content actions.

| Controller / endpoint | Service call and response | HTTP outcomes |
|---|---|---|
| `CustomerAddressesController GET /api/customer-addresses` | `GetAllAsync`; `200` with address list | `200`, `401`, `403` |
| `GET /api/customer-addresses/{id}` | `GetByIdAsync`; `200` with address | `200`, `401`, `403`, `404` |
| `POST /api/customer-addresses` | `CreateAsync`; `201 Created` with response/location | `201`, `400`, `401`, `403` |
| `PUT /api/customer-addresses/{id}` | `UpdateAsync`; `200` with updated response | `200`, `400`, `401`, `403`, `404`, `409` |
| `DELETE /api/customer-addresses/{id}` | `DeleteAsync`; `204` | `204`, `401`, `403`, `404`, `409` |
| `PUT /api/customer-addresses/{id}/default` | `SetDefaultAsync`; `204` | `204`, `401`, `403`, `404` |
| `PackagesController GET /api/packages` | `GetAllAsync`; `200` with package list | `200`, `401`, `403` |
| `GET /api/packages/{id}` | `GetByIdAsync`; `200` with package | `200`, `401`, `403`, `404` |
| `POST /api/packages` | `CreateAsync`; `201 Created` with response/location | `201`, `400`, `401`, `403` |
| `PUT /api/packages/{id}` | `UpdateAsync`; `200` with updated response | `200`, `400`, `401`, `403`, `404`, `409` |
| `DeliveryOrdersController POST /api/delivery-orders` | `CreateAsync`; `201 Created` with order detail/location | `201`, `400`, `401`, `403`, `404`, `409` |
| `GET /api/delivery-orders` | `GetMineAsync(filters)`; `200` with paged results | `200`, `400`, `401`, `403` |
| `GET /api/delivery-orders/{id}` | `GetByIdAsync`; `200` with detail and history | `200`, `401`, `403`, `404` |
| `PUT /api/delivery-orders/{id}` | `UpdateAsync`; `200` with updated detail | `200`, `400`, `401`, `403`, `404`, `409` |
| `POST /api/delivery-orders/{id}/cancel` | `CancelAsync`; `204` | `204`, `400`, `401`, `403`, `404`, `409` |
| `POST /api/delivery-orders/{id}/confirm-delivery` | `ConfirmDeliveryAsync`; `204` | `204`, `400`, `401`, `403`, `404`, `409` |
| `NotificationsController GET /api/notifications` | `GetMineAsync`; `200` with notification list | `200`, `401`, `403` |
| `PUT /api/notifications/{id}/read` | `MarkReadAsync`; `204` | `204`, `401`, `403`, `404` |

`400 Bad Request` covers validation errors; `403 Forbidden` covers an authenticated principal lacking `CUSTOMER`; `404 Not Found` covers a missing or non-owned resource without leaking its existence; `409 Conflict` covers uniqueness/state/relationship conflicts. Shared authorization middleware may return `401 Unauthorized` before a controller is invoked. Framework/model binding determines the precise error body; use the repository's standard problem-details response.

UC-08 identifies the recipient (through the customer or operator app) as actor. The customer-only policy in this module must not accidentally prevent an intended recipient/operator confirmation route; the actor/role contract for that operation needs confirmation before implementation.

## 7. Open issues before implementation

1. **TrackingNumber format:** the ERD example is `DD-202610-0988`, but prefix, date component, sequence/random strategy, collision retry behavior, and privacy/guessability requirements are not finalized. Keep the unique database constraint regardless of the selected format.
2. **SecureCode operational policy:** six random decimal digits are fixed. Confirm the delivery channel, expiry, retry/lockout threshold, secure storage/verification approach, and which actor may submit it. The ERD permits up to ten characters; the UC specifies rejection/counting of wrong attempts but no threshold.
3. **Drone availability at order creation:** confirm whether order submission must also require a currently available compatible drone; package limits are `5000` grams and `40 x 30 x 30` cm.
