# API Contract - Delivery Addresses, Packages and Delivery Orders

Contract for the second API group of SmartDroneDelivery (Sprint 3: LA-21 delivery addresses, LA-22 packages, LA-23 create order, LA-24 update and cancel order, LA-25 order list and details). Backend, web and mobile all build against this document. The backend implements it exactly; the web and mobile teams use the examples as mock data until the real API is ready.

> **Status: proposed, to be confirmed by the team.** Any change goes through a pull request that edits this file, and the change is announced to the team. Items that still need a decision are collected in section 8.

Sources: [functional specification](../design/customer-order-management/functional-specification.md), [class specification](../design/customer-order-management/class-specification.md), [business rules](../requirements/business-rules.md), [ERD](../architecture/erd.md), and the mobile code already merged for LA-21, LA-22 and LA-24.

## 1. Conventions

Everything in section 1 of [auth-api.md](auth-api.md) applies here: base URL, `/api` prefix, camelCase JSON, UUID identifiers, UTC ISO 8601 dates, bearer token, the RFC 7807 error body and the status codes. Only the additions are listed below.

| Item | Rule |
|---|---|
| Role | Every endpoint in sections 2, 3 and 5 is for the `CUSTOMER` role. Another role, or an account that is not `ACTIVE`, gets `403`. |
| Ownership | The customer id always comes from the token (`sub`). The client never sends `userId`, `senderId` or `customerId`. |
| Not yours = not found | A resource that does not exist and a resource that belongs to another customer both return `404`, so ownership is not revealed (BR-CO-36). |
| Validation | Field problems return `400` with `errors` per field. State problems (wrong status, already linked, limit reached) return `409`. |
| Unknown fields | `PUT /api/delivery-orders/{id}` rejects fields that are not in the request with `400` instead of ignoring them (BR-CO-19). Other endpoints may ignore unknown fields. |
| Phone number | Same rule as `phoneNumber` in auth-api.md: 9 to 11 digits. |

### Order status

| Value | Meaning | Customer can update | Customer can cancel |
|---|---|---|---|
| `PENDING` | Created, waiting for the dispatcher | yes | yes |
| `APPROVED` | Approved by the dispatcher | no | yes |
| `READY_FOR_TAKEOFF` | Package handed over at the origin station | no | no |
| `IN_TRANSIT` | Drone is flying | no | no |
| `ARRIVED` | Drone landed at the destination station | no | no |
| `DELIVERED` | Recipient picked up the package (final) | no | no |
| `CANCELLED` | Cancelled (final) | no | no |
| `FAILED` | Delivery failed | no | no |

A new order is always `PENDING`. `COMPLETED` is not an order status.

### Tracking number and pickup code

- `trackingNumber`: unique, generated by the server, format `DD-YYYYMM-NNNN`, for example `DD-202610-0988` (format to confirm, section 8).
- `pickupSecureCode`: exactly 6 digits, generated by the server. It is returned **only** in the response of `POST /api/delivery-orders`. No list, detail, status log or audit log contains it, and no screen for staff shows it (BR-LS-22).

## 2. Delivery addresses (LA-21)

Base path `/api/customer-addresses`. Auth: yes, `CUSTOMER`.

Request body for create and update (`CustomerAddressRequest`):
```json
{
  "label": "Home",
  "contactName": "Nguyen Van An",
  "contactPhone": "0901234567",
  "addressLine": "12 Nguyen Hue, District 1, Ho Chi Minh City",
  "latitude": 10.774321,
  "longitude": 106.703412,
  "isDefault": true
}
```

| Field | Rule |
|---|---|
| `label` | required, at most 50 characters (for example Home, Office) |
| `contactName` | required, at most 150 characters |
| `contactPhone` | required, phone number rule in section 1 |
| `addressLine` | required, not blank |
| `latitude` | optional, -90 to 90 |
| `longitude` | optional, -180 to 180. `latitude` and `longitude` are both sent or both omitted |
| `isDefault` | optional, default `false` |

### GET /api/customer-addresses
Response `200 OK`: array of `CustomerAddress` of the signed-in customer, default address first, then newest first. No paging (a customer has at most 10 addresses).

### GET /api/customer-addresses/{id}
Response `200 OK`: `CustomerAddress`. Errors: `404`.

### POST /api/customer-addresses
Response `201 Created`: `CustomerAddress`, with a `Location` header. Errors: `400` validation, `409` the customer already has 10 addresses.

When `isDefault` is `true`, the previous default address becomes `false` in the same transaction, so a customer never has two default addresses (BR-CO-02).

### PUT /api/customer-addresses/{id}
Full replacement of the fields above. Response `200 OK`: `CustomerAddress`. Errors: `400`, `404`.

### PUT /api/customer-addresses/{id}/default
No request body. Makes this address the default and clears the previous one. Response `200 OK`: `CustomerAddress`. Errors: `404`.

### DELETE /api/customer-addresses/{id}
Response `204 No Content`. Errors: `404`, `409` the address is used by an order (the order history is kept). Deleting the default address is allowed and leaves the customer without a default (to confirm, section 8).

## 3. Packages (LA-22)

Base path `/api/packages`. Auth: yes, `CUSTOMER`.

Request body for create and update (`PackageRequest`):
```json
{
  "packageName": "Birthday gift",
  "weightGram": 850,
  "lengthCm": 25,
  "widthCm": 18,
  "heightCm": 10,
  "packageImageUrl": null,
  "isFragile": true
}
```

| Field | Rule |
|---|---|
| `packageName` | required, at most 200 characters |
| `weightGram` | required, greater than 0 and at most 3000 (3.0 kg) |
| `lengthCm` | required, greater than 0 and at most 30 |
| `widthCm` | required, greater than 0 and at most 20 |
| `heightCm` | required, greater than 0 and at most 15 |
| `packageImageUrl` | optional, a valid URL when sent |
| `isFragile` | optional, default `false` |

The limits are the drone cargo limits (BR-CO-06, BR-CO-07) and are checked again when an order is created.

### GET /api/packages
Query: `available` (optional, `true` returns only packages that are not linked to an order, used by the create order screens; proposed). Response `200 OK`: array of `Package`, newest first. No paging.

### GET /api/packages/{id}
Response `200 OK`: `Package`. Errors: `404`.

### POST /api/packages
Response `201 Created`: `Package`, with a `Location` header. Errors: `400` validation.

### PUT /api/packages/{id}
Full replacement of the fields above. Response `200 OK`: `Package`. Errors: `400`, `404`.

### DELETE /api/packages/{id}
Response `204 No Content`. Errors: `404`, `409` the package is linked to an order (BR-CO-09). One package belongs to at most one order (BR-CO-08).

## 4. Stations for the order screens (needed by LA-104, 105, 108, 109)

The create and edit order screens must let the customer pick an origin and a destination station. Today the mobile edit screen asks the user to type a station id because no endpoint exists. Full station management is Sprint 4, so only this read-only subset is needed now.

### GET /api/landing-stations
Auth: yes, any role. Query: `status` (optional, for example `OPERATIONAL`). Response `200 OK`: array of `StationSummary` sorted by `name`.

The order endpoints only accept stations whose status is `OPERATIONAL`. Who implements this endpoint is open (section 8).

## 5. Delivery orders

Base path `/api/delivery-orders`. Auth: yes, `CUSTOMER`.

### 5.1 POST /api/delivery-orders (LA-23, LA-103)
Create an order.

Request (`CreateDeliveryOrderRequest`)
```json
{
  "packageId": "c41f8b0a-2d37-4a6b-8e1c-5f7a9d3b6e22",
  "originStationId": "7d2e5a90-1b4c-4f38-a6d1-9c8e0b3f5a44",
  "destinationStationId": "a5c9e2b7-3d18-4e60-b4f2-8d1a7c0e9b55",
  "deliveryAddressId": null,
  "recipientName": "Tran Thi Binh",
  "recipientPhone": "0912345678"
}
```

| Field | Rule |
|---|---|
| `packageId` | required, belongs to the customer, within the drone limits, not linked to another order |
| `originStationId` | required, an `OPERATIONAL` station |
| `destinationStationId` | required, an `OPERATIONAL` station, different from the origin |
| `deliveryAddressId` | optional, belongs to the customer |
| `recipientName` | required, at most 150 characters |
| `recipientPhone` | required, phone number rule in section 1 |

The client never sends `customerId`, `status`, `trackingNumber`, `pickupSecureCode` or timestamps.

Response `201 Created`: `DeliveryOrderDetail` with status `PENDING`, one `statusLogs` entry (`fromStatus: null`, `toStatus: "PENDING"`) and one extra field:
```json
{ "pickupSecureCode": "483920" }
```
This is the only time the code is returned, so the app must show it to the customer right away (see section 8).

One database transaction does all of this: create the order, generate the tracking number and the code, write the first status log, and create the customer notification. If any step fails, nothing is saved.

Errors
- `400` recipient data invalid, package not owned by the customer or over the drone limits, a station is not `OPERATIONAL`, origin equals destination.
- `404` package, station or address not found.
- `409` the package is already linked to another order, or the tracking number collided (retry).

### 5.2 GET /api/delivery-orders (LA-25, LA-111)
List the signed-in customer's orders, newest first.

Query

| Param | Rule |
|---|---|
| `page` | optional, default 1, minimum 1 |
| `pageSize` | optional, default 20, 1 to 100 |
| `status` | optional, one status value from section 1. Omit it for all statuses |
| `fromDate` | optional, ISO 8601 UTC, compared with `createdAt`, inclusive |
| `toDate` | optional, ISO 8601 UTC, inclusive, not earlier than `fromDate` |
| `searchKeyword` | optional, at most 50 characters, partial match on `trackingNumber`, case-insensitive |

Response `200 OK`: `PagedResult` of `DeliveryOrderSummary`. An empty result is `200` with `"items": []`, not an error.

Errors: `400` unknown `status`, bad date, `fromDate` after `toDate`, `page` or `pageSize` out of range.

### 5.3 GET /api/delivery-orders/{id} (LA-25, LA-111)
Response `200 OK`: `DeliveryOrderDetail`, `statusLogs` oldest first. Errors: `404` (not found or not yours).

### 5.4 PUT /api/delivery-orders/{id} (LA-24, LA-107)
Update an order. Allowed only while the status is `PENDING`.

Request (`UpdateDeliveryOrderRequest`) contains exactly these four fields:
```json
{
  "recipientName": "Tran Thi Binh",
  "recipientPhone": "0912345678",
  "destinationStationId": "a5c9e2b7-3d18-4e60-b4f2-8d1a7c0e9b55",
  "deliveryAddressId": null
}
```
`destinationStationId` must be an `OPERATIONAL` station different from the origin station. `deliveryAddressId` must belong to the customer when sent. `packageId`, `originStationId`, `status` or any other field is rejected with `400`.

Response `200 OK`: `DeliveryOrderDetail`. Errors: `400`, `404`, `409` the order is no longer `PENDING` when the update is saved.

### 5.5 POST /api/delivery-orders/{id}/cancel (LA-24, LA-107)
Cancel an order. Allowed only for `PENDING` and `APPROVED`.

Request (`CancelDeliveryOrderRequest`)
```json
{ "cancellationReason": "Recipient is not available." }
```
`cancellationReason` is required, not blank, at most 500 characters.

Response `200 OK`: `DeliveryOrderDetail` with status `CANCELLED` and `cancelReason` set. Status change, status log (previous status to `CANCELLED`) and customer notification are saved in one transaction.

Errors: `400` reason missing, blank or too long. `404`. `409` the status does not allow cancelling (`READY_FOR_TAKEOFF`, `IN_TRANSIT`, `ARRIVED`, `DELIVERED`, `FAILED`, or already `CANCELLED`). A repeated request on an already cancelled order returns `409` and creates no second log or notification.

## 7. Differences with the code that is already merged

The mobile code for LA-21, LA-22 and LA-24 was written before this contract existed. It matches the contract except for the address fields. This contract uses the names of the entity, the ERD and the functional specification, so the mobile code needs one rename:

| Mobile today (`CustomerAddress`, `CustomerAddressRequest`) | Contract |
|---|---|
| `addressLabel` | `label` |
| `recipientName` | `contactName` |
| `recipientPhone` | `contactPhone` |
| `streetAddress` | `addressLine` |

The rename touches the two models, the add/edit address page and the address tests. `recipientName` and `recipientPhone` stay as they are on **orders**.

Everything else the mobile code sends and reads already matches: package fields, `cancellationReason`, the update body, the order list filter, `items/page/pageSize/totalCount/totalPages` and the detail fields. The list response shape (a `PagedResult`, not a bare array) must be kept, because the mobile order list handles both.

## 8. Open points

These need a team decision. The contract above states the proposed answer.

1. **Address limit and deletion (BR-CO-04, BR-CO-05).** Proposed: at most 10 addresses per customer (`409` above that); an address used by an order cannot be deleted; deleting the default address is allowed.
2. **Package reuse (BR-CO-08, D-03).** Proposed: one package, one order, never reused, even after the order is cancelled or delivered. The customer creates a new package.
3. **Status filter.** Proposed: one status per request. Several statuses (`status=PENDING,APPROVED`) can be added later.
4. **Tracking number format.** Proposed `DD-YYYYMM-NNNN` from the ERD example.
5. **Seeing the pickup code again.** The code is returned once at creation and never in the detail. If the app is closed before the customer notes it, there is no way to see it. Proposed: also send it in the creation notification to the customer only. Needs a decision.
6. **Stations endpoint.** Section 4 is needed now for the order screens. Proposed: the leader adds it with LA-103 as a read-only endpoint, and Sprint 4 extends it.
7. **Lockout status code.** The pickup code check (UC-08) is not in this document. When it is written, the 10-minute lockout uses `423 Locked`.
